Project-local issue tracker. Persists findings to `.omp/issues/<category>/<id>-<slug>.md` so they survive across sessions and can be triaged, edited, and archived over time. The global id is auto-allocated; the on-disk slug is derived from the title.

<instruction>
The `issues` tool creates and lifecycles issues and sets their board stage; **editing an existing issue (body or other metadata) is done by rewriting its `issues://<id>.md` file with the `write` tool**, not through this tool. Pick the op via `op`:
- `add` — Create a new issue. Required: `category`, `title`, `body`. Optional: `severity` (`low|medium|high|critical`), `status` (`open|in-progress|fixed|wontfix|duplicate`; default `open`), `stage` (`needs-you|up-next|running|awaiting-deploy|deferred`) to file it straight into a board column, `needs` (what the issue waits on: the user's decision, approval or action with `needs-you`, the exact roll with `awaiting-deploy`), `report` (`report://<project>/<slug>` or an `https://` URL), `location[]` (paths or `path:line` refs), `extra` (free-form frontmatter merged into the file). Filing and claiming in one call: `stage: "running"` (or `"needs-you"` with `needs`) claims the new issue for this session exactly as the `stage` op does, so there is no `add`-then-`stage`. A `stage` with a terminal `status` is rejected — archived issues carry no stage.
- `archive` — Move an active issue to `.omp/issues/.archive/<category>/`. Required: `id`. Optional: `reason` (recorded in frontmatter), `status` (default `fixed`). A shortcut for setting a terminal status that also records a `reason`.
- `unarchive` — Move an archived issue back to active. Required: `id`. Optional: `status` (default `open`). A shortcut for reopening (setting a non-terminal status).
- `stage` — Set the issue's `omp-board` column, without reading or rewriting the file. Required: `id`, `stage` (`needs-you|up-next|running|awaiting-deploy|deferred|none`; `none` clears it). Use it when you start work (`running`), hand the issue back (`needs-you`), leave it for a rollout (`awaiting-deploy`), or park it (`deferred`). `needs-you` requires `needs`: exactly what you need from the user — the decision, approval or action they must take — because the board shows that text at the top of the issue. `awaiting-deploy` is where a pending rollout goes, **even one that waits on the user's go**: canary, fleet roll, release, migration apply. Its `needs` is optional and says the exact roll, e.g. `{"op":"stage","id":12,"stage":"awaiting-deploy","needs":"Canary on one cluster with task api:canary, then roll the fleet with task api:deploy."}`. An issue with both a real question and a pending roll is `needs-you`, with the roll named in its `needs` text. `needs` with any other stage is rejected. `running` also claims the issue for this session: from then on its board replies and requeues come to this session. When another live session already holds it the stage is still set and the result says so — two sessions on one issue conflict, so tell the user.
- `list` — Return a summary listing. All params optional: `category`, `archived` (`true`/`false`; default both), `severity`, `status`, `stage` (`needs-you|up-next|running|awaiting-deploy|deferred|none`), `query` (substring search across title/body/frontmatter), `limit`.

**To edit an existing issue, rewrite the whole `issues://<id>.md` file with the `write` tool** — read it first, change what you need, then write the full file back to the `issues://<id>.md` URL (e.g. `issues://14.md`). Always target the id-only `issues://` URL, **not** the on-disk path the read header shows — only the URL write is validated and lifecycle-aware. The frontmatter *is* the metadata layer: changing `title` re-derives the slug, changing `category` moves the file, and setting `status` to `fixed`/`wontfix`/`duplicate` archives it (back to `open`/`in-progress` restores it). The write is rejected if the frontmatter is malformed — a dropped `---` fence, unparseable YAML, or an out-of-enum `status`/`severity`/`stage`. Read with `issues://<id>.md`; browse with `issues://` (active) and `issues://archive` (archived).
</instruction>

<output>
- `add` returns the new issue's id, category, filename, and full `issues://` URL.
- `archive`/`unarchive` return the new location.
- `stage` returns the issue's new `omp-board` column (`#12 stage → running`, or `#12 stage cleared`), plus its `needs` text whenever it carries one.
- `add` with `stage: "running"` or `"needs-you"` says the issue was claimed for this session.
- Writing `issues://<id>.md` with the `write` tool reports any lifecycle effect (moved/renamed/archived) plus the resulting URL.
- `list` returns a markdown summary identical to the `issues://` listing.
</output>

<conventions>
- Categories are kebab-case (`security`, `network-isolation`, `data-correctness`). The reserved name `archive` is rejected.
- Titles are short imperative phrases (~5-10 words); the slug is derived from the first 5 alphanumeric words.
- Bodies are markdown. Recommended sections: a short description paragraph, then a `## Fix` or `## Recommendation` numbered list.
- Use `archive` once the underlying defect is verified fixed (or won't-fix). Prefer `stage: running` (op `stage`) for work in flight; `status: in-progress` is legacy and only triggers the end-of-turn reminder, so move it to a terminal status (fixed/archived) when done or back to `open` when you set it down.
- To close an issue, set its `status` to a terminal value (`fixed`/`wontfix`/`duplicate`) and write `issues://<id>.md` with the `write` tool, or use `op: archive` (which also records a `reason`). To reopen, set `status: open`/`in-progress` and write the file, or use `op: unarchive`.
- Optional `stage` frontmatter sets the issue's state on the `omp-board` list: `needs-you` (blocked on a human decision or action that is not a rollout), `up-next` (the user wants it started), `running` (work in flight across sessions — prefer it over `in-progress` for long-running work), `awaiting-deploy` (the code is done and only the rollout remains — canary, fleet roll, release, migration apply — even when the roll waits on the user's go), `deferred` (parked on purpose). Set it with `op: stage` (`"stage":"none"` clears it) rather than rewriting the file; omit it for plain open work, and archived issues never show a stage. `needs` goes with two stages: required in `needs-you` (what you need from the user) and optional in `awaiting-deploy` (the exact roll to run); both are shown at the top of the issue on the board, and any other stage rejects it. A pending rollout is never `needs-you` unless the issue also carries a real question, whose `needs` then names the roll. A file write that keeps the issue's stage keeps its text if the line was dropped. One that changes the stage keeps `needs` only if you rewrote it: the old line left in place is dropped, and a move into `needs-you` without new text is rejected. An archive drops it.
- Optional `report` frontmatter links the issue to the write-up it came from: `report://<project>/<slug>` or an `https://` URL. Set it with `add`'s `report` param or by rewriting the file; a malformed value is rejected.
- Pending replies, "queued by the user" marks and session claims are machine-local (they live in `~/.omp/agent/issues-inbox/`, never in the issue file). They arrive as a reminder with your next prompt or at turn end, for the issues this session holds — an issue becomes yours when the user asks you to work it and you set it `running`, or when you hand it to the user with `needs-you`. Never write them yourself. An issue this session holds that sits in `needs-you` is listed back to you at your next prompt with its `needs` text: if the user's message answers it, set it `running` before working on it; otherwise leave it waiting.
</conventions>
